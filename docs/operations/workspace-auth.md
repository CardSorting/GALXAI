# Workspace authentication and recovery

<!-- docs-scope: current-guide -->

## Purpose and trigger

Private runbook for the security/access maintainer. Use when Images or Sites allows anonymous entry, loops through sign-in, loses the intended destination, or fails to recover after a session ends; also use it for profile hydration, logout, provider-connection authorization and legacy native-session management. [Current state](../../post-mortem/CURRENT_STATE.md) owns deployment evidence. Deployment and acceptance are tracked separately in current state; local results alone do not establish activation.

## Authority and prerequisites

Images and Sites are discoverable public products whose account workspaces require sign-in. Developer-preview approval, paid entitlement, resource ownership and staff membership remain separate checks. `workspace-policy.ts`, `workspace-session.ts`, middleware and the Images/Sites server pages own entry; browser identity is never sufficient authority.

| Condition | Workspace response | User recovery |
| --- | --- | --- |
| Missing, forged, revoked or anonymous session | GET/HEAD redirects to sign-in; other methods return 401 | Sign in, then return to the requested workspace |
| Valid account or successfully refreshed session | Dynamic private workspace; APIs still check ownership and entitlement | Continue directly; sign-in itself redirects verified accounts |
| Session verification temporarily unavailable | Middleware: generic 503, private/no-store and Retry-After; document requests get a no-JavaScript recovery page. Independent page check: authored recovery within the streamed layout, with no workspace content; the response may already be 200 | Explicit Try again fetches fresh server state; retain existing credentials |
| Active account request receives 401 | Unmount the workspace and focus the sign-in recovery heading | Sign in again; no automatic mutation replay |
| API returns 403, 429 or transient failure | Existing access, cooldown or retry state | Do not start a sign-in loop for a plan restriction or outage |
| Initial browser profile verification fails after server admission | Withhold page content inside the shared shell; show authored session recovery | Retry the profile check, sign in again, or visit Home/public reading pages; no cached grant |

Middleware verifies protected routes before static exemptions, including decoded paths and descendants. Each Images/Sites server page independently verifies again through `WorkspacePageGate`; Library uses the same gate. It catches only the typed expected-unavailability signal; redirect and unexpected exceptions retain their framework semantics. Never infer authorization from HTTP 200 alone on a streamed page. The page gate withholds children on unavailable verification. Route-local unexpected-error boundaries and the root fallback show authored public recovery copy, never raw errors, digests, stacks or clipboard diagnostics. Retry uses a fresh router refresh with boundary reset inside a transition, without automatic timers. The shared product header remains mounted, and the client session check reuses the route loading shell. Supabase sessions use `getUser`, then an uncached owner-bound active-session lookup with independent bounded verification transport. The lookup receives the same verified JWT, accepts no caller-supplied IDs, and returns only a boolean. A missing session is 401; an unavailable lookup, missing migration, denied permission or malformed result is 503. The API resolver, account/profile helpers and server workspace guards all enforce it. Native session creation, lookup, rotation and revocation require a successful authoritative database result, with no cached grant or acknowledgement after a storage failure. Creation persists the complete scope/family record without an upsert fallback. Configured pooled PostgreSQL is the native repository authority; an administrator Data API client is used only when no database URL is configured. Failure never switches transports or grants from memory. Missing persisted scopes grant nothing. Previous tokens are accepted only inside their recorded grace window. Native sessions require active database state, matching owner, signed `accountVerified` provenance and full account scope for browser entry. Native credentials issued before this provenance contract fail closed. Browser recovery presents a finite “sign in again” notice and the regular GALX account methods, preserves the destination, and retires the old alias after successful account sign-in. External provider connection enrollment is closed; an old token or matching email cannot claim an account or transfer its resources. Supabase cookies take precedence over legacy aliases; invalid canonical cookies never fall back to another native account. Cookie presence and user metadata are not grants. Refresh cookies propagate to the continuing request and response. The three exact studio example images and published Site snapshots preserve their public contracts. Auth pages and protected workspaces are uncached; rendered private data must never use shared caching.

## Sign-in and return context

The first-party Sites workspace API accepts the current verified account cookies as well as explicit account bearers. It enforces same-origin intent for cookie mutations, preserves refreshed cookies on all application outcomes, and keeps verification outages at 503 instead of misclassifying them as expired credentials. The browser profile deliberately contains no bearer token; do not require a client bearer mirror for workspace entry. Standalone Sites content/domain APIs retain their separate contracts.

The page offers Google, GitHub, email/password and an existing-account email link. The server decides whether an existing session can continue. Temporary verification failure keeps the regular sign-in form available; an inline connection notice offers a session retry without clearing the form. The form continues to its validated destination after a server-verified browser profile recovers. Local storage alone never redirects or grants entry. Password success requests a fresh document so middleware and the destination page verify the session again.

Canonical account entry uses `/login` and `/signup`; `/auth/signin` and `/auth/signup` remain permanent redirect aliases. `/auth/callback` retains its URL for existing provider and email configuration. Return targets must be same-origin relative paths and cannot recursively target auth, login or signup routes, including encoded variants. The shared builder leaves path separators readable (`/login?next=/sites`) and encodes nested query delimiters and fragments. The default Images destination needs no `next` parameter. Workspace-generated targets preserve the saved Site path, known starter/refinement, or exact `/images/library` and `/images/favorites` destination, discarding unrelated query fields. Create/My images/Favorites are native links with browser history; search, sort and pagination remain local state. Old `?view=library` bookmarks migrate to `/images/library` before entry; duplicate or unknown legacy views resolve to Create. Migration redirects have empty bodies and private/no-store headers, and project only supported fields. See [readable URLs](../maintainers/readable-urls.md) for the complete navigation and compatibility contract. Auth notices use finite authored messages; arbitrary query errors and provider diagnostics are never rendered.

Middleware passes exact signup/account-callback entry and login with a single `reauth=1` through without refreshing the previous account; server pages/profile APIs retain their own verification. Ordinary login retains middleware refresh so rotated cookies reach the browser before the server-page verification. This prevents expired old credentials from delaying recovery or racing a new exchange. The account callback exchanges a single PKCE code through a request-scoped client independent of data-query circuit/rate limits, under one ten-second deadline. It does not automatically replay the exchange. Both callback middleware and handler enforce no-referrer. Redirects are private/no-store, carry accumulated SDK cookie writes, and expire legacy aliases only after success. Cancellation, missing/duplicate codes and exchange failures use finite notices plus `reauth=1`, so a still-valid prior account cannot swallow the error by redirecting back to its workspace. Codes, verifier material and provider messages never enter response bodies or redirect destinations.

Email links disable automatic account creation, keep the callback destination and use the same confirmation for an unknown address. A sixty-second resend affordance and a per-form in-flight lock reduce accidental repeats; server rate limits remain authoritative. No email delivery/provider configuration was changed. Password managers can use named username/current-password fields, paste and password visibility. Validation associates labels/errors, focuses the first invalid field and announces request failures; confirmation and session expiry move focus to their headings. Controls support reduced motion and reflow.

Client 401 handling is owner-scoped and ignores aborted responses. It complements server enforcement and cannot revoke already delivered bytes. Existing per-tab, per-account draft storage remains; automatic recovery never submits a second generation. Another account does not inherit the previous account's mounted workspace. Losing connectivity alone does not log a user out. The Auth provider verifies its public profile through `/api/auth/session`; cached SDK data and local storage are candidates, never authority. A cookie-only verification starts independently of SDK initialization. First-party account requests do not carry a captured SDK bearer token that could override refreshed cookies. Identical in-flight checks share one promise; changed credentials synchronously invalidate older requests inside the SDK event callback, before deferred verification begins. An obsolete success or 401 cannot restore or remove the newer account. Abort/revision guards reject obsolete requests, initialization cannot overwrite a later auth event, and visible focus/visibility checks are coalesced and spaced at least thirty seconds from the last attempt, including failures, without polling. A genuine offline-to-online transition bypasses this cooldown. Persisted pagehide cancels old verification; persisted pageshow checks logout markers again and forces current-cookie verification even after a recent success. History restoration retains same-account content while rechecking; server APIs still enforce current authorization and already delivered content cannot be recalled. Each verification performs at most two read-only requests within a shared 25-second deadline. Only transport failures, 429 and 5xx can retry automatically, once; Retry-After is respected up to three seconds, with longer backoff left to later recovery. Invalid credentials, other 4xx and malformed profiles do not retry. Refreshed or cleared SDK cookies propagate even when a later active-session check fails. An account change clears the previous owner before validation. The legacy outbox key stores only an owner ID, with no token, email or role. Real hosted session acceptance remains separate.

`AuthProvider` supplies state and actions without replacing its children. The root layout's `AuthSessionContent` withholds page content on initial verification failure, keeping product navigation and the footer mounted. Home, the exact curated public reading allowlist, and the exact `/login` and `/signup` entry routes remain available during that failure; private account and authoring pages stay withheld. Entry exceptions confer no session or API permissions. Recovery links use the finite `reauth=1` flag: the login page and client form suppress existing-session redirects so a failed browser check cannot bounce the user back to the workspace. Normal login retains automatic continuation. Explicit credential sign-in still verifies the destination in a fresh document. The account slot offers Retry account rather than claiming a guest or authenticated state. A previously verified same-account view remains mounted during a transient resume failure and shows a nonblocking connection notice. The stable wrapper preserves mounted editors and current input when the notice appears or disappears; each API request still checks current authority. A changed account clears the previous identity before validation. The full recovery view offers Try again, Sign in again with the supported destination, and Return home; the no-JavaScript middleware response offers equivalent choices. Neither recovery path creates a new grant from cached identity.

Recovery announces pending, offline and unsuccessful retry states through one polite status region outside busy content. Manual retry is synchronously guarded against duplicate activation and retains keyboard focus while pending. A newly mounted full recovery view focuses its heading only when focus is on the document body or main container, leaving active navigation focus alone. The loading shell announces a longer-than-usual wait after six seconds and offers Home. Timers never retry a render or replay a mutation. The single delayed read-only profile retry and coalesced online/focus verification remain distinct from manual route refresh.

## Sign-out and session authority

Sign out means **this browser**. The client immediately removes account content, writes a pending marker shared with other tabs, stops local refresh, and sends a same-origin DELETE. The server verifies the current credential before revoking it: Supabase uses Auth sign-out with `local` scope; native sessions use owner-checked session revocation. Raw session IDs, API keys, body credentials and URL query tokens are not account credentials. Cookie mutations require exact same-origin intent; explicit CLI bearer requests may omit Origin but cannot supply a foreign Origin. Failures use finite errors and never report success after a database/Auth failure.

Successful or already-invalid logout clears SDK cookie chunks, verifier cookies and legacy aliases, then opens a new sign-in document. A pending logout hides all account content and blocks workspace entry even after reload. **Retry sign-out** resumes the request after an outage; pending credentials are retained only so revocation can be retried. Other tabs remove private content on the shared marker. History restoration checks the marker even when a storage event was missed. An SDK SIGNED_OUT event after failed revocation cannot remove the explicit Retry sign-out state; it is not server confirmation. Another sign-in clears the marker through an explicit user action. Server pending-cookie checks remain available if browser storage is blocked.

The content gate also owns pending/failed sign-out recovery, including on public pages. The public shell stays mounted while account content is removed; public-reading exceptions apply only to profile unavailability, never to pending logout. This presentation change does not alter revocation or successful-sign-out criteria.

Successful sign-out requires Auth local logout **and** confirmation that the current session is no longer active. Subsequent GALX account requests reject copied access JWTs before their cryptographic expiry. The check binds `session_id` and owner to the authenticated Data API claims against `auth.sessions` and rejects anonymous users and elapsed `not_after`. Other browser sessions stay active. An Auth acknowledgement that leaves the session active returns 503 and keeps retry available. This does not cancel requests already authorized, erase delivered data, or alter JWT semantics for unrelated consumers. Existing server-mediated data permissions remain separate. No global sign-out, password-change policy, session lifetime configuration, MFA enrollment or full Supabase device inventory is implied. Native session-management endpoints remain specific to verified full native credentials.

Legacy elevation is closed with 403: possession of a session, a supplied duration, or an API key cannot prove recent authentication. Provider connection routes are closed and grant no sessions or sudo window. Operational activity/posture, vault and internal training operations require the explicit server-only administrator credential; no built-in secret, vault-root fallback, user metadata or account role can grant operational access; ordinary account or native sudo state cannot grant it. No synthetic symmetric key is advertised as public JWKS. Restricted tokens must stay within parent scope and expiry, cannot manage account sessions, and have bounded input/lifetime.

## Provider connections and account permissions

Verified Supabase accounts with confirmed email own account/staff operations. Native token email and editable metadata cannot authorize staff privileges. External provider connections are closed: OpenAI/ingest aliases and provider OAuth URL/PAR/callback/refresh handlers return finite 410 responses before processing credentials. They cannot create sessions, change account cookies, import a shard or renew a provider token family. GALX account login/callback, logout and session refresh remain separate and continue normally.

Provider credentials require manual sign-in in the owning desktop and explicit central review/registration through the fixed Premium/Standard monitor. Later renewal uses an explicit saved-sign-in update. The retained controller's Enroll shard flow applies only to eligible unassigned accounts; neither workflow follows from GALX account sign-in. See [manual registration](../maintainers/RELAY_CREDENTIAL_ENROLLMENT.md) and [central authority](../reference/relay-account-management.md). This private operational policy is not exposed through public response diagnostics.

Device approval creates a separate restricted credential, capped at one day and parent expiry; it never copies the current browser token. It awaits the existing durable approval RPC and binds the approving owner. An explicitly declined code revokes the newly issued credential. Polling does not fall back to process memory after a durable denial/failure; issued credentials are verified again and projected to the public token contract. The active-session migration does not change device approval/polling RPCs. Those route tests stub RPC results; deployed RPC policy, one-time consumption and cross-process behavior require separate database acceptance. These legacy preview routes are not evidence of a public standards-certified OAuth authorization server.

## Active-session rollout and recovery

The base `20260913201023_account_session_liveness.sql` introduces the claim-bound definer and public invoker wrapper. Apply `20260916161120_isolate_account_session_lookup.sql` after the later operational migrations: it moves the existing definer, with its owner and body unchanged, into the dedicated non-exposed `galx_account_auth` schema and retargets the same public wrapper. Only `authenticated` receives schema USAGE and helper EXECUTE; no browser role receives schema CREATE or session-table access. The operational `private` schema stays unavailable to ordinary accounts. Both account and session IDs come from verified request claims. The lookup reads existing primary-key records and performs no account/session data rewrite. Two-second lock and ten-second statement limits bound each migration.

Do not restore broad `private` schema usage as an auth repair. The September 16 [diagnosis](../../post-mortem/incidents/2026/2026-09-16-session-recovery/permission-diagnosis.json) confirmed that manual-desktop/foundation hardening revoked the original helper's schema access and caused verified-account lookups to raise 42501. The repair preserves both boundaries. Its DOWN restores the old dependency and retains data; with operational grants still denied, it intentionally returns to unavailable verification. Reapply the repair for recovery instead of weakening entry checks. Do not run the original liveness DOWN against the repaired chain.

Run `test:auth:db` against the final migration chain before replaying any older migration. It verifies active lookup, native creation/rotation/revocation, ownership, schema/function/table privileges, repeated operational-schema denial, same-token replay, idempotence and rollback/reapply with unchanged function identity. Reapplying the original liveness migration before the first assertion previously masked the broken grant. Run `db:test` separately and retain unconditional elevation denial. Verify the linked pending migration set, apply only the reviewed repair with vault configuration preserved, inspect grants and run advisors. The existing application RPC contract is unchanged; this database repair needs no application redeployment. A removed or broken lookup must remain recoverable 503. Keep the repair through application rollback. Confirm existing-browser entry and, using isolated owned sessions, local logout rejection and independent refresh. Never revoke a user's working browser as a fixture.

## Deployed cache boundary

Cloudflare Browser Cache TTL must respect existing origin headers (`browser_cache_ttl: 0`). A fixed browser TTL can replace `private, no-store` on static-looking workspace paths even when authentication correctly redirects. Keep the application's private response policy authoritative; changing application headers alone cannot fix a downstream override. Preserve immutable caching on versioned public assets. Review any Cache/Page Rules for equivalent overrides before changing them; do not run unrelated provisioning or storage-hardening scripts to repair this setting.

Run `node scripts/verify-workspace-cache-http.mjs https://galx.ai` against the canonical production host. It performs read-only GET/HEAD checks on all three workspaces and misleading extensions, with anonymous and legacy-cookie prefetch requests, plus sign-in and a versioned asset. Private responses must remain private/no-store and must not be a shared-cache hit. Canonical-host redirects on other aliases require separate redirect-chain checks. The September 13 release caught and repaired a four-hour browser TTL override; retain that failed acceptance alongside the successful rerun. Already delivered browser content and prior client caches cannot be recalled by a configuration change.

## Procedure

1. Start with FM-ACCESS-002 and the [incident](../../post-mortem/incidents/2026/2026-09-13-workspace-auth/README.md). Inspect read-only raw GET/HEAD responses with no cookies, forged cookies and an authorized test account. Record only aggregate status/redirect/cache results; omit tokens and user data.
2. Run `GALX_JSDOM_MODULE=/absolute/path/to/jsdom/lib/api.js npm run test:auth:recovery` for SDK initialization independence, Strict Mode, concurrent checks, synchronous account/token changes, obsolete 401/success responses, transient failures, focus bursts, offline reconnection, persisted history, missed logout events and failed-sign-out fencing. `test:auth:sessions` includes cookie-only transport, finite retry/backoff and cookie propagation and callback circuit-isolation/deadline/safe-redirect regressions. Run `node --import tsx --test scripts/test-url-navigation.ts`, `npm run test:auth:sessions`, `npm run test:auth:db`, `npm run db:test`, `npm run test:image:security`, `npm run test:developer-preview`, `npm run test:preview-admin`, `npm run test:egress:transport`, `npm run test:image:scale` and `npm run test:sites:workspace`. Run TypeScript and lint. These exercise auth, sanitized responses, owner boundaries and existing recovery budgets.
3. Make an isolated production build using `scripts/build-ci.mjs` with `CI=true`, no dotenv files and no real service credentials. Never deploy that synthetic build. Run `node scripts/verify-auth-entry-server.cjs /absolute/path/to/isolated-build`; it listens on localhost port 3427 and substitutes synthetic Auth results while blocking outbound fetches. Stop it after verification.
4. Run `node scripts/verify-workspace-auth-http.mjs http://localhost:3427`. This checks actual compiled redirects, valid/invalid/unavailable sessions, unsafe return targets, methods, assets and selected private markers. Run `scripts/verify-auth-entry-ui.ts` with `tsx`, installed Chrome and `GALX_BROWSER_MODULE`/`GALX_AXE_MODULE` paths when Playwright/Axe are outside the repository. It checks desktop/phone, stale identity, password/email-link flows, 401 removal, draft retention, 403, outages, failed sign-out across reload/tabs, credential-cookie clearing and reflow. Account entry/profile/logout use the compiled server with synthetic Auth transport; product API operations and browser Auth calls are intercepted. The browser fixture bypasses production CSP for its fake Auth host; raw HTTP checks retain real response headers. It does not certify live provider redirects or email delivery.
5. For direct browser inspection without external requests, `node scripts/verify-session-recovery-server.cjs /absolute/path/to/isolated-build` binds localhost:3428. Visit `/__session_fixture/entry` to retain sign-in during a server/browser outage, or `/__session_fixture/browser` for client verification failure after server admission. Restore only this synthetic service with `POST /__session_fixture/recover`, then activate Try again and verify the original destination. Inspect desktop and mobile reflow, keyboard focus, one status region and 44px recovery controls. Never deploy either fixture. Run `node scripts/verify-url-navigation.mjs` for direct Library/Favorites entry, native links/new tabs, browser history, retained results/drafts, refresh and session-expiry destinations. Then run `node scripts/verify-workspace-navigation.mjs` against that same compiled fixture. It exercises separate server and browser verification failures, repeated manual recovery, offline state, retained shell, safe Home, Images/Sites draft continuity, 403, delayed/history navigation, reduced motion, six-second wait feedback, themes, forced colors and 320px doubled-text reflow. Inspect completed JSON and captures under `.impeccable/review/auth-entry/` (or `GALX_AUTH_REVIEW_OUTPUT`) and `.impeccable/review/workspace-ux-audit/` (or `GALX_WORKSPACE_REVIEW_OUTPUT`), not an interrupted partial run. Scan compiled rendered/browser assets with the private-content build guard. Legacy workspace fixtures that seed only local storage must be adapted to verified server sessions; never disable entry guards to make a fixture pass.
6. After deploying, run the canonical-host cache acceptance above and an owned live account test for entry, legacy replacement, local logout, copied-token denial and independent-session refresh. Scan the actual rendered pages and linked assets. Semantically reconcile affected guides, retain source/build/evidence hashes, append the incident journal, attest affected domains, then run `docs:sync`, `docs:check` and `test:docs`. Keep production activation separate from local fixture success.

## Stop conditions

Stop release acceptance if any unauthenticated workspace returns content, any forged/cross-account identity succeeds, redirects loop or leave the allowed origin, private responses become publicly cacheable, diagnostics appear publicly, or existing-account access fails. Fix the boundary before acceptance. An Auth outage should remain recoverable unavailable; do not substitute a cached grant.

## Recovery and rollback

Deploy the reviewed middleware/pages and client entry flow together after the active-session migration. Verify anonymous denial and existing-account entry on the deployed revision, both products and a saved Site, direct navigation and client navigation, sign-out and cross-tab expiry, callback return and refresh. Real OAuth/email delivery, physical-device input and screen-reader acceptance are distinct from synthetic checks. Generation, billing and publication are not needed for account acceptance. Record those untouched scopes as limits.

Keep `/login`, `/signup`, the two image subpages and their compatibility redirects together during application rollback; new bookmarks must remain resolvable. No auth provider configuration or database rollback is required for the URL migration. Rollback may revert the form presentation or client recovery wrapper while retaining verified server entry, private response handling and API ownership checks. Never roll back to cookie-only entry or the anonymous workspace. The incident remains open until deployed denial and valid-session access are recorded; recovery does not close unfinished prevention work.

## Pattern rationale

[Slack’s connection recovery](https://slack.com/help/articles/360001603387-Manage-Slack-connection-issues) informs visible connection feedback and an explicit recovery action without equating an outage to sign-out. [Slack's sign-in guidance](https://slack.com/help/articles/212681477-Sign-in-to-Slack) makes workspace context and provider/email entry familiar; [Notion](https://www.notion.com/en-gb/help/log-in-and-out) also documents provider and email sign-in. GALX adapts those interaction patterns without copying their architecture or claiming identical security. [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) informs finite errors and password-manager support; [W3C form notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) informs error association and focus. [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide) and [existing-account OTP options](https://supabase.com/docs/reference/javascript/auth-signinwithotp) inform the integration. [MDN pageshow](https://developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event) defines the persisted history-restoration signal used for revalidation. [GitHub session management](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/viewing-and-managing-your-sessions) informs explicit per-device/current-browser meaning; [GitHub sudo mode](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode) illustrates fresh verification instead of self-asserted elevation. [Supabase sign-out scopes](https://supabase.com/docs/guides/auth/signout) and [session lifetime guidance](https://supabase.com/docs/guides/auth/sessions) define the integration's revocation limits. These are design choices, not a claim of certification or measured conversion improvement.

The [workspace render investigation](../../post-mortem/incidents/2026/2026-09-13-workspace-render/README.md) and [navigation guide](../NATURAL_NAVIGATION_AND_OMNISEARCH.md) own the new page-outage regression fixture and release limitations.
