# Billing pages and navigation

<!-- docs-scope: current-guide -->

Private maintainer contract. The current source separates billing tasks into stable pages. [Current operating state](../../post-mortem/CURRENT_STATE.md) distinguishes local verification from a hosted release. This guide is not imported into application content.

## Destinations and user paths

| Destination | Address | Main task |
| --- | --- | --- |
| Overview | `/billing` | Review plan and credit summaries; choose a task |
| Plan | `/billing/plan` | Review access, renewal/end date, payment recovery; start or manage Pro |
| Credits | `/billing/credits` | Review balance and usage; choose a one-time top-up |
| Transactions | `/billing/transactions` | Filter wallet activity, load older rows, export loaded rows |
| Invoices | `/billing/invoices` | View up to 20 recent invoices; use Stripe for older invoices/downloads |
| Payment settings | `/billing/payment-methods` | Open the restricted Stripe portal to manage saved payment methods |

Pricing, home and generation upgrade actions link directly to Plan. API-key navigation, signup credit links, SDK balance recovery and the CLI top-up command link directly to Credits. Team ledger links open Transactions; assisted team/enterprise purchase links contact support. Both search menus expose all six tasks using the canonical destination registry. The CLI prints an amount-prefilled Credits URL and requires signed-in quote review; it does not calculate or promise an account-specific bonus. The primary account link still opens Overview. Plan and prepaid credit remain separate commercial contracts. A wallet balance never implies Pro access, and purchasing either does not grant developer API approval.

The layout has persistent native links, one active destination, a breadcrumb, task-specific heading and account context. Desktop uses a navigation rail; mobile wraps the same links without hiding tasks inside a menu. Loading and error boundaries remain within the billing shell. Error copy never renders exceptions, stack traces or operational explanations. Billing metadata describes plan, credit and payment capabilities without historical pricing/rebate claims.

## State and recovery

`BillingProvider` is keyed by account and remains mounted across billing destinations. It owns current billing data, the transaction filter, typed credit amount and wallet/payment-action state. Superseded reads are canceled, have a finite deadline and cannot overwrite newer results. Failed refreshes retain last checked data with an explicit notice. A changed filter shows the last successful filter until its new result arrives; export and pagination are disabled when rows do not match, a request is pending or the read failed.

Page navigation preserves credit drafts and existing durable retry identities. Reload or departure from Billing does not promise in-memory draft retention; the account-scoped checkout retry record remains in session storage. The single Credits form first reads its current record, then a valid record from the retired API-key form for the same account and amount. It promotes the same request ID without starting a new payment. Confirmed payments and explicit completed/expired-attempt responses clear both namespaces. Malformed, future-dated and expired records are ignored. Account replacement or logout removes the account provider and its state. Navigation remembers supported receipt/plan return URLs in memory and clears them when account identity changes. Pending receipts never allow an automatic second checkout. The receipt status endpoint remains the confirmation authority.

Overview Refresh updates both its plan and credit summaries; each read keeps its own loading and failure state. Plan reads are independent of wallet availability. Plan management and payment settings remain reachable during a read failure; the API decides whether an authenticated payment profile exists. With a confirmed absent profile, Payment settings explains how to start one and links to Plan and Credits. The application never fabricates saved-card details or treats a wallet read as payment authority.

The existing `/api/billing` response remains an owner-scoped allowlisted snapshot; no ledger, settlement or entitlement authority changes. The private plan checkout table adds only the return contract described below; it is not part of this response. Billing pages expose a public shell to anonymous visitors with a sign-in destination, never account data. The APIs independently reject absent, forged and wrong-owner authority. Responses stay private/no-store and pages noindex. Ordinary account users do not gain administrator access.

## Checkout and compatibility

`src/lib/billing/navigation.ts` owns the finite destination map used by UI entry links, metadata, navigation and search. `compatibility.ts` is the middleware-only owner of retired addresses. Middleware resolves supported GET/HEAD query and retired-route redirects before React rendering with private/no-store 307 responses; the response body is empty or the same supported public destination. This avoids competing streamed and client redirects; mutation requests do not receive these redirects. Legacy `/billing?plan_checkout=returned|canceled` leads to Plan. Supported `checkout`, `session_id` and valid `amount` parameters lead to Credits. Only supported single values are forwarded; arbitrary destinations, tokens, duplicate state parameters and malformed amounts/receipt identifiers are discarded. Parameters select a display/recovery path, never authorize payment or prove success.

Old `#plan`, `#balance`, `#history` and `#payments` bookmarks are forwarded in the browser to Plan, Credits, Transactions and Payment settings. New credit Checkout sessions persist `/billing/credits` in the existing attempt metadata; new Pro Checkout attempts persist `/billing/plan` in the private `return_path` column. Existing attempts retain their exact provider return parameters. Older plan rows have NULL for this column and retain the historical `/billing?plan_checkout=…#plan` contract. The compatibility handler resolves those URLs to the current task. Stripe rejects changed inputs for the same idempotency key, so never backfill old attempts with new paths. Unknown stored paths fail closed.

New portal sessions return directly to Plan or Payment settings. The provisioning script uses Plan as its default return. The optional live transport probe requires the same restricted portal configuration as the app; running it remains a separate live action, not a local regression test. No existing Stripe Dashboard configuration needs changing just to resolve old returns.

Old reports, promo, expenses and audit-log addresses resolve to Transactions; payment-related retired pages resolve to Payment settings; invoice detail aliases resolve to Invoices. Existing team redirects retain `/teams/seats`, and the assisted enterprise alias retains Pricing. The global `/vault/*` redirect excludes the exact deposit bookmark so middleware can sanitize it before redirecting to Credits. Other vault redirects retain their existing destination. The retired page implementations are removed, including `/keys/top-up`, `/vault/deposit`, `/checkout`, `/checkout/success` and the old `/lumi` purchase page. Old credit links retain only supported amount/receipt fields; `plan=pro` goes to Plan and unsupported or ambiguous purchase plans go to Pricing. `/lumi` also resolves to Pricing. Deleted duplicate top-up/paywall/quick-peek components cannot mount another payment form. Internal historical protocol identifiers and financial records remain intact. These compatibility redirects do not imply that retired tax/budget/webhook features have been implemented.

## Verification and release

Run `npm run test:billing:lifecycle`, `npm run test:auth:sessions`, TypeScript and scoped lint. Navigation fixtures cover canonical destinations, old returns/anchors, duplicates, malformed input and dropped private fields. Existing billing suites cover provider-state/portal safety, public DTOs and webhook signature/mode/body boundaries. Also run `npm run db:verify`, `npm run db:test`, `npm run test:sites:plans:db`, and `node --import tsx scripts/run-supabase-integration.ts --billing`. They use disposable databases and simulated Stripe; plan tests verify NULL and canonical return contracts, exact retry parameters, forbidden paths, denied browser roles and retained rollback evidence.

Build in a disposable copy with `CI=true node scripts/build-ci.mjs`, no dotenv or live credentials. Run `node scripts/verify-billing-ux.mjs /private/tmp/galx-billing-audit-<validation-directory>`. The runner uses the tracked synthetic auth server, local Chrome and Playwright/Axe; optional `GALX_BROWSER_MODULE` and `GALX_AXE_MODULE` specify module paths, and `GALX_BILLING_REVIEW_OUTPUT` selects a new evidence directory without overwriting prior captures. It checks raw private HTTP responses, all six destinations, active navigation, 1440/390/320px, 200% text, retained drafts/retries (including the retired API-key form identity), failure recovery, empty states, receipt navigation and retired entry redirects. It blocks external requests and stops its server/browser. Captures and JSON are under `.impeccable/review/billing-pages/`. Do not deploy the synthetic build.

Apply `20260916003207_billing_canonical_returns.sql` to the application database before deploying the compatible checkout writer. It adds a nullable, constrained text column without a backfill or privilege change, with a two-second lock timeout and ten-second statement timeout. A lock timeout requires diagnosis before another attempt. Verify the column/check and retained forced RLS; ordinary users still cannot read payment-attempt storage. No tax, product-price, balance, access-policy or live payment change is part of this migration.

Deploy canonical pages, entry links, compatible checkout readers and middleware together. After an authorized release, verify signed-in direct entry, search and API-key entry, a prior bookmark and an existing return URL, account replacement/logout, and rendered/linked-asset boundaries. Actual Stripe-hosted navigation and live receipt settlement remain separate acceptance. Source/build verification does not establish live rollout.

For rollback, revert presentation only while retaining resolvable new addresses, old-return redirects and the reader for both stored return contracts. The paired down script intentionally retains the additive column and all attempt evidence: dropping it or deploying the old handler after new attempts exist would change Stripe retry parameters. Do not weaken ownership, private caching or payment confirmation.

## References and scope

The design adapts [Notion's billing summary](https://www.notion.com/help/billing), [Linear's billing management and history](https://linear.app/docs/billing-and-plans), and [Vercel's separate usage destination](https://vercel.com/docs/pricing/manage-and-optimize-usage). These are public interaction precedents, not evidence of their architecture or a measured conversion benefit. GALX retains its own current pricing, access rules and hosted payment contract.
