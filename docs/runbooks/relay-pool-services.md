## Purpose and trigger

Owner: Relay operator. Use this private runbook for the local Premium service under [ADR 0159](../adr/0159-local-mac-relay-operation.md), with the account and credential boundaries in [ADR 0153](../adr/0153-central-account-authority-isolated-relays.md). Local operation uses the reviewed Premium image set in [local images](../../docker/relay-pools/local/images.json), including the connection-lifecycle monitor and subsequent shared-quota and generation-compatibility runtime updates. Earlier runtime pins remain dated rollback artifacts.

The [original service release](../../post-mortem/releases/2026-09-15-relay-services.json) distinguishes applied databases, implemented/tested source and built images at its closed-gate observation. The owner selected the existing Mac as the operating host because hosted alternatives are unaffordable or have not worked for this use. The cloud candidate remains unprovisioned. This local setup can recover while the Mac is powered, awake and signed in; it is not independent hosted uptime, and source changes do not qualify provider generation or authorize an application cutover.

The execution project contains only a fixed identity and execution reservations/outcomes with opaque central references. It has no account registry, credentials or second capacity ledger. Main-project accounts are never copied into it. Installation scope comes from a hashed central principal, not request JSON, a browser selector or a session variable. Provider account class is separate from GALX customer billing tier.

The full schema, management and health contract is [account and registration management](../reference/relay-account-management.md). Each runtime hosts an in-process engine per eligible account inside its own container; it has no Docker socket and does not create per-account worker containers.

The local trust boundary is the owner's Mac plus a dedicated Premium Colima Linux VM with its own **Docker daemon**. The monitor needs that VM's Docker socket for manual desktops. The socket is powerful host authority, so Compose networks alone are insufficient. Docker documents both [daemon access implications](https://docs.docker.com/engine/security/) and [per-service secret mounts](https://docs.docker.com/compose/how-tos/use-secrets/). File secrets require restrictive host ownership readable by container UID 1000; they are not encrypted by Compose. Host credentials and topology remain in private service files and this private runbook.

The active workstation must not be interrupted for a drill. Physical reboot/shutdown, power loss, logout, sleep/wake, host-network disruption, destructive host disk pressure and disruptive shared-daemon restarts are **UNVERIFIED — DEFERRED BY OPERATOR**. Do not change system-wide power settings. Use [non-disruptive service acceptance](mac-self-hosting.md#non-disruptive-resilience-acceptance) with isolated fixtures; a provisional assumption that documented startup survives a normal reboot is not a passed test or production-readiness evidence. Existing service operation commands below remain for deliberate operation, not authorization to disrupt unrelated work during testing.

## Procedure

### Local Premium operation on the owner's Mac

The local layout uses Docker Desktop for the central authority and TLS proxy, and one Colima profile `premium` for the Linux kernel, Docker daemon and disk. The VM has two CPUs, 3 GiB memory and a 30 GiB data disk. It does not mount Mac directories or forward the Mac SSH agent. The Mac administrator and host remain a common trust boundary; this is local VM isolation, not a separate physical machine.

The installation uses separate native central and Premium clusters. Central alone has its restricted control login and vault configuration; the separate whole-web app retains its reviewed application-owner authority. Native database connections and local authority HTTPS verify certificates/hostnames. Each CA is trusted only by relevant clients; no system-wide trust change is required. The authority's private key stays on the Mac. Its HTTPS endpoint is `https://localhost:13443` from the Mac and `https://host.lima.internal:13443` from the VM, forwarding only fixed protocol routes without retries. Premium alone reaches its own fixed database on 55433; central DB remains denied to the VM.

The [October 17 continuation](../../post-mortem/releases/2026-10-17-local-account-migration.json) records Premium's drain, source fence, final copy and native switch. Later [retirement evidence](../../post-mortem/releases/2026-10-17-premium-retirement-account-email.json) records private downloaded/decrypted recovery and verified hosted deletion. The [central cutover](../../post-mortem/releases/2026-10-17-central-native-cutover.json) records native central/Auth/web/Nova activation and its separately open account corrections. Native image pins preserve prior queue/outcome behavior. Thirty local checks pass after central activation, including ownership, monitor authorization, isolation and verified database TLS. Both provider sign-ins expired before the first switch; preflight sent no generation. Renew only through the owning desktops and explicit reconnect, without changing account policy or discovering ambient host credentials.

For everyday access, open **GALX Monitors** from the Mac menu bar, Applications or its Desktop shortcut, then choose **Open Premium**. The **GALX Premium** app is searchable in Spotlight and can be kept in the Dock. The launcher has no account registry or combined browser session. Its status checks the relay and monitor independently and says when one or both do not respond; listener health does not establish provider readiness.

The launcher uses a native menu-bar status surface and a separate online setting, patterns familiar from [Docker Desktop](https://docs.docker.com/desktop/use-desktop/#the-docker-menu) and [Tailscale](https://tailscale.com/docs/features/client/manage-preferences). Opening Premium starts its stopped VM/services and the shared central dependency when necessary, verifies the accepted VM/daemon identity, absent host mounts, active isolation service and reviewed images, then requests a scoped browser ticket. Startup and stop actions share a lock across the menu app, CLI and supervisor so they cannot change the same stack concurrently. No account action or inference request is retried by the launcher.

Cold startup brings the Premium monitor up first, reads its centrally authorized last runtime heartbeat using a temporary session, and revokes that session. If its listener remains unavailable after the bounded startup wait, recovery restarts only the monitor when its container is still running; missing or stopped containers are started by Compose. Before replacing an image or recovering an unavailable runtime, the supervisor checks the authorized last heartbeat, waits until the existing 60-second ownership fence has elapsed, and rechecks central health and container identity. A healthy container with a stale tag or immutable image ID is gracefully stopped and recreated from the reviewed manifest after handoff; a matching but unresponsive runtime is restarted in place, while a missing or stopped runtime is started by Compose. This preserves the existing central claim fence and runtime volume; the database still denies an active or competing owner. Invalid/future timestamps, a changed central health state or mismatched installation identity stop runtime recovery. A first cold-start experiment reopened the monitor while its runtime correctly refused a premature claim; the corrected order waits for handoff instead of weakening that rule.

**Open at Login** and **Keep Premium online** are separate settings and default to off on a new install. Open at Login launches only the menu app. Keep Premium online starts a per-user macOS `launchd` supervisor at sign-in; it recovers Docker Desktop, the Premium VM, central services, relay and monitor with bounded backoff. Before bringing services up, recovery synchronizes the canonical local Compose overlay into the Premium VM so its `unless-stopped` policies apply even when the VM has been stopped. Central Compose health checks follow Docker's [health check and `service_healthy` startup pattern](https://docs.docker.com/compose/how-tos/startup-order/) and distinguish running containers from healthy services: the authority must answer its fixed local liveness check, and the TLS proxy must reach that authority through a certificate-verified local health request. Compose starts the TLS proxy after the authority reports healthy; the supervisor then waits up to 45 seconds for all configured central services to become healthy. If any is marked unhealthy, it restarts only those unhealthy services and waits up to 60 seconds again. For the Premium monitor and relay, the supervisor checks the fixed liveness endpoint and requires each running container tag and immutable image ID to match the reviewed manifest. A live Premium runtime additionally requires a centrally authorized, non-future ownership heartbeat younger than 45 seconds for this installation. A stale heartbeat therefore enters relay recovery even while the HTTP listener answers. This check does not depend on provider credentials, enabled-account count or execution gates: an intentional pause or expired account does not cause restart churn. Missing, malformed, foreign or inaccessible control evidence blocks recovery for administrator inspection. A healthy but stale image triggers a service-scoped replacement; an unavailable matching image triggers a bounded service recovery. Ambiguous container states fail closed into bounded supervisor retry. Runtime replacement/recovery first completes the authorized heartbeat handoff, then rechecks central health, image identity and current ownership freshness before Compose starts a replacement. If the heartbeat recovers during the wait, the launcher leaves the matching runtime running. Recovery succeeds only after listener/image verification and a fresh authorized heartbeat; liveness alone cannot complete it. The supervisor rereads the manifest during each reconciliation; reload its launch agent after changing supervisor source itself. No monitor, relay or central health check proves database, account, provider or model readiness; authenticated operation checks remain separate. Retry backoff is jittered and capped at five minutes after jitter is applied.

The menu reports relay and monitor health separately from supervisor state, shows a fixed recovery category and retry estimate, and reports whether the AC idle-sleep assertion process is active. Battery state explains that the assertion applies on AC only. A private heartbeat keeps a planned backoff distinguishable from a supervisor that stopped reporting; the menu does not expose subprocess output or arbitrary diagnostics. If it shows **Status unavailable** or **Review Settings**, use the CLI `status` command before intervening. Both login preferences validate their expected LaunchAgent identity and command before removing a file; a conflict is left untouched for operator review. Quitting the menu app does not stop the supervisor. The supervisor starts only after the owner signs in; it is not a root daemon or a substitute for automatic login. The current enablement and service health are recorded in [current state](../../post-mortem/CURRENT_STATE.md). Build and install the local, ad-hoc signed apps with:

```sh
npm run relay:monitors:build
npm run relay:monitors:install
```

This requires macOS 13+, Xcode command-line tools, Node, Colima and Docker Desktop. The build command writes into `.relay/monitor-apps`; installation places both apps under the current user's `~/Applications` and adds a Desktop shortcut. The installation records this workspace and Node path. Reinstall after moving the workspace or changing Node installations. To stop recovery, turn off **Keep Premium online** first. To remove the menu launcher, turn off **Open at Login**, quit GALX Monitors and remove both app bundles and the Desktop shortcut. This does not remove accounts, VMs or service state.

The CLI remains available from the repository root:

```sh
npm run relay:local -- up
npm run relay:local -- status
npm run relay:local -- verify
npm run relay:local -- open premium
npm run relay:local -- stop
```

`up` starts Docker Desktop, the Premium VM and the three local service components when needed. It preserves the active Docker Desktop context. `status` reports power, supervisor, central, VM, relay and monitor separately and remains useful while services are stopped. Its separate Premium relay connection line confirms authorized ownership freshness; the listener health line alone does not establish that connection. An unavailable control read reports Status unavailable without changing runtime authority. `stop` refuses while Keep Premium online is enabled; turn that setting off first. `open` uses the same start-on-demand behavior as the apps and creates a one-use 60-second operator sign-in link in the default browser, without printing the ticket or storing long-lived keys in the browser. The browser consumes it automatically and immediately removes it from the address bar, including when reopening a previously authenticated page or reusing its tab. Switching to a viewer ticket revokes the prior operator session. Sign-out remains explicit; there is no automatic sign-in merely from visiting a plain monitor URL.

The Premium monitor remains at `http://127.0.0.1:13311` and uses the fixed `galx-monitor://open/premium` app link. Its signed-out/expired-link screen rejects every other destination, query, fragment, userinfo or port. Browsers may show their normal external-app confirmation. The link contains no credential. A fresh ticket still comes from the monitor after central authorization. The opener writes only pool, time and a browser-launch-request flag to a private receipt; that flag does not prove the browser completed sign-in. Runtime port 13301 remains loopback-only and requires its inference key.

If the app cannot open the monitor, check power and local service availability, then choose **Open Premium** to retry. For a live listener with unconfirmed ownership, use the [stale ownership failure mode](../../post-mortem/failure-modes/controller.md#fm-ctrl-003--live-runtime-loses-central-ownership-freshness), inspect private status and use the corrected `up` path. Do not renew the heartbeat manually, bypass the central fence or reconnect valid accounts as a runtime repair. Keep Premium online retries failed recovery with bounded exponential backoff and jitter; it never repeats an account action or inference request. The opener recovers a startup lock only when its recorded owner no longer exists. An uncertain or malformed lock, changed VM identity, missing image or isolation failure requires operator inspection; do not delete identities, disable isolation or substitute another configuration. The menu displays allowlisted health states only and does not expose subprocess output or credentials.

For best availability, keep the Mac connected to AC power with the lid open and its owner account signed in. `caffeinate` prevents idle system sleep only while on AC power; macOS can still sleep on lid close, low battery or system policy. Network interruption, host shutdown or user logout can suspend service. This is a low-cost local operating mode, not a cloud uptime guarantee.

`verify` checks actual VM/daemon identity, absent Mac file mounts, running-image matches, private container mounts, persistent firewall hook ordering, authenticated Premium monitor roles and database TLS. It writes private evidence to `.relay/service-deployment/local-acceptance.json`. This is a bounded local acceptance check; it does not qualify provider generation or turn on execution.

Automatic activation and execution gates are separate from keeping local processes online. Do not run `serve-local` as part of installation or recovery. If a gate/policy change is later authorized, first run fresh local `verify`, inspect its private evidence, then follow the gate procedure deliberately. Existing account pauses, reconnect intent and manual installation holds remain authoritative. The public application must not be pointed at these localhost URLs. [Automatic activation acceptance](../../post-mortem/releases/2026-09-16-relay-automatic-activation.json) is dated evidence and does not accept this supervisor change.


After turning off **Keep Premium online**, this stops the Premium runtime/monitor stack, the local central stack and the Premium VM, freeing VM memory while preserving account records, desktop homes, state volumes and disks. `up` restores the services; monitor browser sessions need fresh opener links. Do not delete the profile, volumes or `.relay/service-deployment/authority.json` as a reset. The existing legacy Docker Desktop services are separate and are not stopped by these commands.

For reinstalling local component files, use `npm run relay:local -- install` only with the existing three narrow configurations and loaded reviewed images. Premium's active configuration must retain `native-postgres-v1`, its own database URL/CA and restricted role; do not regenerate it from the old hosted export. It verifies the central and Premium identities, installs matching private files under `/opt/galx/config`, and retains either exact known firewall policy. The local overlay takes runtime and monitor tags from `docker/relay-pools/local/images.json`; the CLI verifies their exact image IDs. Build, test, inspect and load replacements into the destination VM before updating this manifest and reinstalling the overlay. Retain the preceding image and manifest as dated rollback evidence. Do not rewrite an earlier release record. The original hosted exporter reads only allowlisted vault settings; it does not perform a native database cutover. Preserve `.relay/service-deployment/local-tls`, native database certificates and private permissions; leaf certificates expire after one year. Renewal needs an inspected replacement and coordinated client trust, not disabled TLS verification.

For a runtime update, build only the changed target from `docker/relay-pools/services-bake.hcl` under a new explicit `TAG`, inspect/verify it, and load it only into the Premium Colima VM. Retain the previous manifest and image. The current reviewed release is pinned in `docker/relay-pools/local/images.json`; the September 25 queue image remains retained as rollback evidence. The Premium runtime places authenticated non-stream generation requests in its in-process BroccoliQueue, backed by BroccoliDB under the existing `/state` volume. The queue does not add a database project, container, deployment target, account ledger or cross-pool scheduling; streaming chat keeps its existing path. Runtime ownership and execution recovery complete before the queue store opens, and readiness requires both workers to run. Queue admission is capped at 128 live jobs, eight per owner, and 32 waiting/delayed images. Each queued request has a 120-second wait deadline. A timeout or disconnect cancels only unclaimed work; after claim, the execution ledger continues to govern the result. Worker claims renew a 90-second lease every 30 seconds, bounding unclean-start recovery without shortening a live generation. The queue workspace is private to the runtime UID, rejects symlinks, and compacts after eight response acknowledgements, 128 queue mutations or 30 seconds rather than rewriting the database on every response. These modes do not encrypt the volume from a host administrator with disk access. Workers drain for at most 330 seconds; Compose allows eight minutes for total shutdown. Graceful shutdown closes queue admission while existing workers process already accepted work as the HTTP listener drains. After connected requests complete or expire, workers stop claiming and drain active handlers. Unclaimed jobs left in `/state` resume on the replacement runtime with their original deadlines; callers whose deadline expires before claim receive `not_accepted` and can retry with the same idempotency key. For a quiet installation without application traffic, confirm no active work and let the old runtime drain before replacement; preserve gate/policy intent. For serving traffic, first apply a deliberate maintenance hold and verify work has drained. Stop only the affected runtime, update the pinned manifest, then run `npm run relay:local -- up`. Startup enforces the central ownership wait and checks the running container against the reviewed image tag and immutable ID. The supervisor rereads the manifest on each reconciliation and gracefully replaces a healthy-but-stale runtime after the ownership handoff; `npm run relay:local -- up` uses the same path on demand. Reload the supervisor after changing its own source so the running launch agent uses the reviewed logic. Preserve `/state`, desktops, credentials, assignments and accepted work. Waiting jobs resume from that retained volume with their original deadlines. After restart, a worker checks the recorded claim timestamp before entering the relay handler and returns `not_accepted` without dispatch for a job that expired before claim; an uncleanly interrupted active claim is reconciled after its lease expires. Dispatched execution remains governed by the existing execution records and is never automatically redispatched after an uncertain outcome. Run `GALX_RELAY_IMAGE_MANIFEST=docker/relay-pools/local/images.json node scripts/verify-relay-service-images.mjs` and `npm run relay:local -- verify`. Keep unchanged runtime/central/monitor pins. The [shared-quota contract](../reference/shared-quota-recovery.md) owns recovery and continuation; caller distribution and actual workload qualification remain separate.

**Clean-checkout source boundary.** Both the application and relay image declare immutable BroccoliDB and BROCCOLIQUEUE HTTPS source archives in their respective package manifests and lockfiles. Application source imports their package names. The relay builder installs its locked development dependencies and aliases their package source entrypoints for bundling; it never copies ignored sibling repositories or requires their local generated output. Its runtime stage installs production dependencies only. When updating either package, publish that repository first, pin the exact reviewed commit and integrity in each consuming lockfile, then run package checks, the application build and the clean artifact checks below. The monitor copies Docker CLI 29.5.3 from its digest-pinned official image; it does not depend on retention of an exact version in a mutable Alpine package index.

The local nftables chains use priority **−150**, after connection tracking and before ordinary Docker filtering. The active known native-database variant adds only gateway port 55433 to the existing central HTTPS exception on 13443; central PostgreSQL, SSH and other Mac/LAN access remain denied. `scripts/install-relay-local-isolation.py` retains either exact known variant by default; changing variants requires its explicit reviewed flag. A draft −210 rule interrupted SSH before credentials were delivered; it was corrected and recovered via Lima early-boot provisioning. Do not move connection-state rules before the connection-tracking hook. Colima's actual shared gateway is `192.168.105.2`; a conflicting gateway left Premium DNS stale during first setup and was reconciled to its saved configuration. Confirm DNS, scoped database TLS and central access after a VM reboot or Colima upgrade. Colima profile configuration is documented in its [official configuration guide](https://colima.run/docs/configuration/).

Accounts separates **Saved state**, **Relay confirmation**, and **Request status**. Applied requires a non-future heartbeat under 45 seconds old, matching revision and matching epoch. ### 6. Preserve the application boundary

This local operation change does not reconfigure application URLs, tunnel ingress, DNS or customer routing. The runtime remains loopback-bound on this Mac; do not point a public application directly at `127.0.0.1` or treat local menu status as external reachability. Any existing, separately reviewed ingress continues to own its narrow route and must pass its own service and customer-response acceptance before a change.

The application supports `GALX_ISOLATED_RELAYS_ENABLED=1`, `GALX_PREMIUM_RELAY_URL` and `GALX_PREMIUM_RELAY_KEY`. Configuration is server-only. Premium handles text, Sites and images; it bypasses application account selection/decryption and a second account lease while acquiring the existing central account lease. Existing customer quota, Sites fair usage and billing policy remain separate.

Images can be connected independently with `GALX_PREMIUM_IMAGES_ENABLED=1` plus only `GALX_PREMIUM_RELAY_URL` and `GALX_PREMIUM_RELAY_KEY`. This selects Premium for both availability and generation, skips legacy account selection/leases, and leaves text/Sites on their existing configuration. A missing or invalid Premium configuration fails closed; it never falls back to legacy. On the local split-service install, `GALX_PREMIUM_RELAY_CONFIG_FILE` may point to the private Premium runtime component file so the inference key is read without duplicating it into `.env.local`; never commit or publish that file.

The server-side adapter uses bounded service discovery instead of trusting one port: it probes explicit `*_RELAY_URL`/`*_RELAY_URLS` values, private discovery/config-file endpoints, configured `*_RELAY_PORTS`, and an optional loopback-only `*_RELAY_PORT_RANGE` (maximum 32 candidates). Image candidates must pass both a relay health endpoint and the image availability contract; a healthy but unrelated controller is therefore not selected over a working image runtime. The winning endpoint is cached briefly, failed endpoints enter a cooldown circuit, and a later availability check re-evaluates the candidate set. Within a Premium pool, the runtime also keeps capability state per assigned worker and workload: a classified image capability or worker failure opens only that worker's bounded circuit, while an unknown/ambiguous result remains request-scoped and does not remove future capacity from that worker. Later new work is selected from eligible workers. Image dispatch is single-flight per worker/shard even when the worker's general text capacity is higher. A bounded in-process image admission queue (maximum 32 pending, maximum 8 per owner, 120-second absolute wait) holds requests before worker forwarding and wakes one fair owner at a time after the prior image reservation releases. A single workload-level recheck also notices capacity released by another workload without creating a poller per request; it never resets the original wait deadline. `AdmissionLifecycle` is the single request-side state/cleanup authority: it records received, queued, admitted, dispatched and terminal outcomes, owns the scheduler reservation, distinguishes known-not-dispatched from ambiguous POST outcomes, and releases capacity once. Queue expiry/full conditions return generic retryable backpressure; no worker session, central execution grant or upstream POST exists until the request owns a slot. The queue is process-local rather than a durable task broker, so a restart drops only unforwarded waiters and callers may safely retry those `not_accepted` responses. Runtime shard ownership is ephemeral and survives registry refreshes without being restored from checkpoints, so discovered worker rows cannot erase a live reservation. An explicit fleet/control-plane failure is distinct from an ordinary worker attempt failure and is the only class that should stop a bounded population. The worker signal is a fixed private vocabulary; provider messages, credentials, topology and private headers are removed before an application response. A generation `POST` is never replayed on another endpoint after dispatch could have started; the next explicit attempt performs fresh discovery. Keep discovery settings server-only and use the narrowest candidate set that represents the installed service. See the [admission lifecycle reference](relay-admission-lifecycle.md) for the complete transition and cleanup contract.

The installed image connection uses the existing Cloudflare tunnel with a separate server-only origin, `https://images-service.galx.ai`. Preserve exact reviewed host/path rules for the installed workload protocol and a final deny rule. The October 7 connection acceptance observed `/health/live`, `/health`, authenticated `/v1/models` and `/v1/images/availability` through that origin; `/health/ready` remains private. The earlier image-only path set is dated deployment evidence, not the complete current rule set. Inspect current private ingress configuration before any change; connection repair does not widen or replace it. Runtime inference authentication and browser-origin rejection remain required. Existing legacy ingress is retained, and neither monitor nor central authority is published. `galx-image-tunnel` runs on Docker Desktop with the pinned `cloudflare/cloudflared:2026.8.3` image, read-only filesystem, dropped capabilities, no-new-privileges and only its private token file mounted. It restarts unless explicitly stopped. Keep `.relay/service-deployment/image-tunnel-token` mode 0600, out of Git/deployment; never pass the credential in a command argument or browser URL. Restart an inspected stopped connector with `docker --context desktop-linux start galx-image-tunnel`. Preserve the private before/configuration records. Availability reads in-process evidence directly: fresh successful synthesis is true; fresh negative evidence or unavailable execution is false; absent/expired evidence is null. It cannot call a nonexistent inner-worker availability URL or infer image denial from chat inventory. No GET generates an image. Explicit centrally admitted generation can qualify unknown capability. ## Recovery and rollback

For October 17 placement, preserve both native databases and accepted/uncertain records. A hosted-only image is not compatible rollback. Use a native-compatible image/current destination, or contain admission and reconcile data explicitly. Premium's source is deleted and central's retained source is stale/write-guarded and paused under Free; never repoint to either as an image rollback. Premium's approved off-device recovery/deletion is complete; central's fresh consistent off-device snapshot also restores all 196 table hashes, owners, effective ACLs and RLS. Database recovery does not certify VM disks, queue volumes, complete secret recovery or provider readiness.

For the image-only cutover, stop new image admission before rollback. A prior application release uses the legacy connection and does not establish working image availability. Prefer a forward correction; do not silently redirect accepted work or remove its receipts. Restore a preceding Premium image only after draining and ownership handoff; `generation-20260916-r2` retains the known broken availability read. Keep connector/DNS configuration until original-operation requirements are reconciled. Never remove the shared legacy tunnel as an image rollback.

Central grants last 30 seconds, renew every eight seconds, and have an independent expiry timer plus a ten-minute central maximum. A failed renewal aborts active upstream work. Runtime ownership heartbeats expire after 45 seconds and a new epoch cannot take over until the prior owner is stale for 60 seconds. No new grants or refreshes are issued during central outage.

Execution identity is persisted before acquisition and bound before provider I/O. Terminal writes serialize and original lease settlements retry through one bounded maintenance pass with backoff; while a terminal write or acquired-but-unbound lease is unconfirmed, new local admission stops. A durably completed local slot is released before remote settlement completes. A crash recovers old in-flight records as unknown with neutral provider evidence, never as permission to redispatch. Nullable success is preserved through durable finish, pending settlement and the central release function: `null` leaves account success/failure history unchanged. Confirmed provider completion uses `true`; attributable provider availability failure uses `false`. Cancellation, deadlines, socket loss and local authorization/admission failures must not manufacture provider failure evidence. Previously retained outcomes and counters stay unchanged. A crash between central acquisition and local binding may leave a lease to expire; it cannot start duplicate work. Retain canonical leases and execution records for investigation.

Pause/revoke/remove changes central revision, blocks renewal and stops the owning in-process account engine. This differs from the retained controller's worker-preserving maintenance hold. Credential material already delivered upstream is not remotely invalidated by a database write. Stop/fence the owning desktop/host or revoke the provider session when hard revocation is required. Historical artifact/receipt access after worker removal or epoch replacement can remain unavailable; records are retained, and uncertain execution is never retried automatically. There is no cross-host job migration.

Use `npm run relay:services:gates -- close` to disarm automatic activation and deny registration/execution, then wait for grant expiry and verify worker shutdown. Stop only the matching Compose stack. Preserve its volumes, manual desktop homes, central assignments and receipts. Paired rollbacks retain identities/history and close protocol access; they do not restore broad writers or account borrowing. Do not revert to an application that routes assigned accounts through the legacy path.

The connection-lifecycle rollback retains irreversible tombstones and rejected-token evidence, closes both gates and revokes the private protocol. Do not install an older runtime while reopening execution: it cannot report the new connection state. Reopen only with compatible schema/services and fresh acceptance.

The management rollback closes both gates and revokes the control protocol while retaining its columns and immutable journal. It does not undo revocation or restore removed accounts. Close services before restoring the preceding central/monitor image pins from the dated console evidence; reopen only after a compatible migration and fresh acceptance. An image rollback alone does not undo central state.

Generation-compatibility rollback to `quota-20260916-r2` restores the known provider-parameter rejection; use it only under a deliberate execution hold, not as a serving recovery. Preserve volumes, unknown receipts, account intent and original execution identities. Prefer a verified forward correction.

Shared-quota rollback restores the previous `connections-20260916` runtime pins from retained installation evidence while keeping execution closed. It restores the earlier Premium selection behavior and lacks the new continuation/output guarantees. Preserve state, cooldowns, identities and unknown outcomes. Caller rollback must preserve new checkpoints and avoid feeding unfinished history to an old automatic loop; forward recovery is preferred. Earlier function-tool rollback recipes are historical evidence, not the current compatible release procedure.

Automatic-activation rollback closes registration/execution, disables the private protocol and retains policy columns, account intent and operation history. Restore compatible code and fresh verification before rearming. An ordinary restart or heartbeat never overrides `close` or the registration-only hold. Re-arming preserves existing account pauses.
