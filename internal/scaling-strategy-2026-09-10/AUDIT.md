# Scaling readiness audit

**The September 10 snapshot was a workable single-provider foundation, with material gaps for a broad flat-rate launch with paid overage.** The highest-priority gaps concern charging correctness and public response contracts. Adding providers before closing them would increase financial exposure and the number of incompatible responses the service must handle.

Evidence is from revision `4587642` and isolated synthetic probes on September 10, 2026. P1 means a material paid-expansion or information-boundary blocker; P2 means significant correctness, maintainability or operational work. No P0 incident or production exploit is established. Tests below reproduce local behavior, not customer loss or the current deployed fleet.

## Sites implementation disposition — September 11

The later [fixed-price Sites implementation](../../docs/adr/0134-fixed-price-sites-generation-with-opaque-provider-quotas.md) addresses a narrow content path; it does not close every general-inference finding below. Supplier concentration is accepted for this scope. Exact provider quota/cost information and a second supplier are not release prerequisites for it.

| Findings | Disposition for fixed-price Sites |

| A02–A05, A11: reservations, durable settlement, usage and attribution | Reserve in the account wallet before dispatch; persist per-operation completion evidence; settle the original fixed quote once. Missing token usage remains null; uncertain completion stays reserved. General chat/image batch accounting is outside this change. |
| A06, A12, A14: public responses, tool and identity boundaries | Sites has strict text/quote/cost/error DTOs and account authorization. It does not claim a general chat/tool repair, supplier privacy attestation or native Codex provider compatibility. |

| A16: verification | Local application/adversarial, database, companion, production-build and network-disabled container recovery checks are recorded separately. They do not establish a live rollout or fleet SLO. |

## Second-pass counterchecks

**There is distributed admission.** The chat route calls `evaluateAndAcquireDistributedGate` before synchronous routing, and it returns explicit idempotency conflicts. It would be inaccurate to characterize the entire system as relying only on process-local counters. This gate does not connect the wallet hold methods to inference, and async submission skips this specific synchronous gate. Admission and worker execution each need explicit financial semantics.

**Payment fulfillment is materially stronger than inference metering.** It uses a transaction, event and payment locks, identity/amount checks, duplicate handling and reconciliation of refunds/disputes. A database exception requests retry rather than creating process-local payment money. Preserve that pattern. The gap is that usage metering and monthly subscription grants are different paths, not that all financial handling is absent.

**Image publication already establishes the right boundary pattern.** Raw HTTP tests check binary artifacts, re-encoding, metadata removal, JSON field allowlists, signed downloads, errors and async retrieval. The image router sanitizes artifacts before storage. This is reusable precedent for chat, not evidence that the chat path automatically inherits it. Image charging still reaches the same post-execution batch buffer.

**Transport tests validate useful behavior.** The checked relay suite requires terminal completion, preserves usage, handles cancellation and deadlines, and prevents replay of ambiguous image synthesis. The stream metering probe shows that downstream accounting nevertheless ignores available structured usage in favor of byte estimates. A passing transport contract does not prove a correct financial contract.

**Public text model names and reference prices are not assumed fictitious.** Current official documentation corroborates the local Sol/Terra/Luna names and listed rates. That does not validate every legacy alias, the identity of every execution path, or GALX's negotiated costs. Model naming and execution provenance remain distinct checks. [Source S17](SOURCES.md#s17).

**A clean static asset scan does not clear dynamic responses.** The isolated build's 616 JavaScript/HTML files contained none of eight selected operational markers. The actual chat route still exposed private fields under a synthetic quota failure. Both results are true; the static test simply does not exercise that dynamic branch.

**Last night's successful checks are scoped historical evidence.** The September 9 documents distinguish source updates, worker/controller state and actual deployments. They explicitly leave some billing reconciliation and cross-restart outcome guarantees open. This audit does not transform those observations into current inventory or a universal availability guarantee.

## September 10 broader-expansion readiness assessment

| Dimension | Conclusion at the audit snapshot |
| --- | --- |
| Continue the existing service | Preserve operation; remediate A02–A08 with bounded releases. No production outage established here. |
| Sell seamless paid continuation | Blocked on durable accounting, contractual price authority and real spend limits. |
| Add one provider to an internal evaluation | Appropriate after isolated adapter scaffolding and supplier qualification; no customer traffic needed. |
| Enable backup for a limited paid cohort | Requires A01–A06 and exact capability/price/privacy acceptance. |
| Launch many providers or unrestricted flat-rate usage | Unsupported by current correctness and economic evidence. |

For the broader chat/accounting roadmap, the audit proposed addressing A06 independently, then A02–A05 and A11 as one coherent accounting change. A07–A09 govern the commercial pilot. A10/A12/A13/A14 are part of the second-provider contract, not cleanup that can wait until after it serves customers.
