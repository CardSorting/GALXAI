## Latest finding: a workflow around the existing relay

Use `relay text → validated content schema → fixed template → installed Sites helpers → customer-owned Sites tools`. The runner controls actions and tool results; the model never needs to emit function calls or receive tool-result messages. This applies the Sites skill requirements to a specific delivery workflow, rather than implementing general autonomous skill execution.

The [live evidence](sites-automation/live-observations.json) records one real relay request, 7,097 ms generation time, a 1,857-byte static draft and successful official packaging. The authenticated Sites tool host recorded zero model turns and zero unexpected model requests. Nine offline guardrail tests passed. No Site was created, no source was pushed, no version was saved and nothing was deployed. The local archive lacks a registered project, source commit and saved version, so packaging is not deployment proof.

This machine's separate Sites connection is still required. A relay-only **model supply** is sufficient for the demonstrated path; a relay key by itself does not grant Sites account access. Start with a customer-local companion using that customer's installed plugin and connection. A hosted multi-customer publishing service would require an additional supported account-connection and ownership design that this experiment does not establish.

The next functional gate is connecting the durable core to one isolated customer-owned publication and update. The next commercial gate is trustworthy usage and enforceable server-side spending limits: the successful request returned no usable token total, and the requested output limit is not verified as enforced by the relay. Sell a bounded, repeatable deliverable only after those costs and support effort are measured. Do not infer an unlimited allowance from this demonstration.

## Can users use the Sites skill with the relay?

**Yes for the demonstrated local workflow; not yet for a complete hosted delivery or the native Codex agent loop.** “Sites with the relay” contains several different product promises:

| User workflow | Finding | Release status |
| --- | --- | --- |
| GALX workflow uses relay text to generate content and a separate authenticated Sites tool host to execute predetermined steps | Live relay generation, schema validation, static rendering, authenticated Sites read and official local packaging succeeded without a Codex model turn. | Preferred bounded implementation; publication, recovery and cost enforcement remain gates |
| User runs Codex with their own Sites connection and selects GALX for model requests | Both Sites skills remain enabled; an actual Sites inventory read succeeds under a custom-provider configuration. The real CLI's model request receives 404 from the current relay. | Not ready as an end-to-end GALX workflow |
| User builds/hosts a Site through their own Sites account, and the application's server calls GALX for inference | Existing relay text transport passed a local synthetic-provider test. A hosted Site calling the authenticated public GALX API has not been tested. | Candidate for a narrower runtime-inference pilot |
| GALX centrally creates/publishes Sites for arbitrary customers using the relay's account | No Sites RPC surface, workspace executor, per-customer Sites authorization or ownership contract was established. | Not an available feature; not the recommended first implementation |

The bounded workflow is the preferred first architecture under the relay-only constraint. Preserve publishing identity and Site ownership with the customer. Native Codex compatibility remains a separate investment if funded demand requires its broader agent behavior; it is no longer a prerequisite for a template-based Sites pilot. The relay need not become a general-purpose Sites execution service.

The same-session probe used a distinct synthetic provider key with `requires_openai_auth: false`; it did not send a ChatGPT credential as the relay's API key. Codex continued using its existing login for its own Sites connector. This is evidence that selecting a custom provider need not remove Sites from this account's runtime. It is **not** evidence that a GALX API key grants Sites access, that API-key-only users receive Sites, or that every account and CLI distribution has the bundled plugin.

The CLI also requested `/v1/models`, which the direct worker returned as 404. The direct-worker observation must not be presented as a missing public model catalog. The inspected public application has no Responses route or rewrite to one. The earlier compatibility fixture did not call the deployed GALX service.

The documented current Codex provider protocol is `responses`, including for custom providers.[^5] Changing the base URL to `/v1/chat/completions` or installing the Sites skill cannot repair the missing protocol. The relay currently forwards text-oriented requests, and its model capability inventory is not a registry of executable Sites operations.

The public chat route and `OpenAIAdapter` accept/forward tool fields toward the relay, making silent loss further downstream a material compatibility defect. A separate CLI completion helper explicitly prohibits skills and tools; it is not an existing Sites runner.

### Native Codex compatibility: a separate workstream

1. **Current native CLI limit:** the working Sites plugin and connection do not make the present relay compatible with Codex model turns. Since the relay is the only available model supply, implement the demonstrated bounded workflow first. Do not make switching providers a dependency of this plan.
2. **Compatibility engineering:** reject unsupported tool requests explicitly instead of accepting them and silently losing semantics. Preserve existing supported text behavior. If native Codex support is funded, qualify a bounded Responses contract at the customer API and through the relay: tool definitions/choice, call IDs, argument streaming, `function_call_output`, continuation, terminal events, usage, cancellation and errors. Do not solve this by exposing a generic authenticated MCP proxy.
3. **Acceptance before a customer pilot:** actual Codex completes a deterministic function-call/result round trip through GALX; adversarial public-response and cross-tenant tests pass; an interrupted request cannot replay a publishing action; a bounded live inference probe succeeds with measured usage and no credential leakage. Build and browser-asset checks apply before shipping application changes. The current fixture establishes none of those unperformed release gates.
4. **Then run one customer-owned Sites pilot:** use synthetic data, a separate project, explicit spending limits and a small revision allowance. Verify build, saved version, requested audience, deployment and a subsequent update. Record who owns the Site, who can edit it, what happens when access is revoked, and how the source can be handed over. Do not migrate GALX's operational repository for this experiment.
5. **Evaluate the narrower runtime path independently:** let a Site's authenticated server call the public GALX API with a bounded project credential kept in hosted secret storage. Verify a real hosted request, visitor authorization, rate/spend limits, cancellation and sanitized errors before documenting it as supported. Never place a relay administrator key or shared GALX credential in browser code. Sites documents hosted environment/secret configuration, but actual hosted connectivity remains to be tested.[^1]

Agent-compatible model transport is a dependency of native Codex inference, not of the new bounded workflow. Further plugin discovery is unnecessary for the observed machine/account. Hosted runtime inference is another independent experiment; it should not be confused with automating a Site's creation and publication.

## Correct the quoted argument

The official Sites guide directs creation, saving, deployment and management to ChatGPT web or desktop, and describes no standalone CLI management view. It allows local CLI editing/testing. This does not prove that every terminal session lacks every Sites tool, but it does not document general headless publishing support either.[^1]

The plugin guide documents a CLI `/plugins` browser and a new session after installation. A shared catalog is not a promise that every capability runs on every surface. Installing a package is also not equivalent to receiving authenticated backend access.[^2]

Accordingly, replace “if Astra lists deploy, we are done” with “the session exposes a potential publishing operation; now verify connection, authorization, artifact compatibility and the intended audience.” Connection and a real read operation have now passed in both environments. No public standalone Sites deployment API or `codex sites deploy` command was established by the documentation checked. The working local route is Codex's authenticated Sites tools, accessed through the bundled plugin and runtime.

## Commercial implications

A stronger product hypothesis would be: **GALX delivers and maintains a specific client workflow, with reviewable releases and explicit operating limits.** Sites could reduce the work needed to deliver that product. Customers would pay for requirements, integration, verification, supported changes and continued usefulness. A publish button alone does not establish recurring willingness to pay.

The relay experiment narrows the positioning further: **help teams operate customer-owned AI applications with project budgets, attributable usage and supported revisions.** OpenAI already supplies the Sites skills to this account; merely repackaging access is a weak differentiation hypothesis. GALX must earn its fee through a measured customer outcome or operational benefit. Keep customer Sites entitlements and hosting costs separate from GALX's fee and inference charges. Do not advertise a GALX subscription as including unlimited Sites hosting or access to someone else's Sites account.

The scope distinction also affects cost. Customer-local workflow execution avoids hosting every development workspace and account connector, although companion maintenance, plugin compatibility, support and billing still cost money. A centralized publishing runner adds workspace lifecycle and identity isolation; both designs need durable jobs, artifact handling and side-effect recovery. Do not incur the larger hosted obligation merely because one account can list Sites. No maintenance saving, conversion gain or recurring willingness to pay has yet been measured.

This potentially expands the agency thesis from financial operations into application delivery. That is a scope change to validate, not an automatic improvement. If each application needs different integrations and extensive maintenance, the result is a services business whose labor must be priced. If a small number of templates repeatedly satisfy the same paid job, a more repeatable product may emerge. Measure that difference before bundling unlimited revisions.

The opportunity is to reduce delivery cost while keeping a price tied to buyer value. Using the existing model's hypothetical $75/hour labor cost, saving two hours on setup improves one-time contribution by $150 before additional tools, hosting, migration and maintenance expense. It does not add $150 to recurring monthly margin. Reducing recurring support by fifteen minutes would add $18.75/month, again before those extra costs. Neither saving has been measured.

Use this incremental calculation:

`net contribution improvement = measured labor avoided − extra platform costs − extra maintenance − allocated migration cost`

Do not assume the ChatGPT subscription funds unlimited visitor inference or all application infrastructure. Account entitlements and application running costs require separate evidence. Building and hosting through the same vendor also does not create an independent model supplier; it leaves the original provider-concentration question unresolved.

The Help Center describes beta allowances shared across an account, with limits capable of affecting public availability. No account-specific capacity or stable scaled price was established here. That makes unlimited hosted client applications an unsupported offer.[^3]

## Material documentation conflict

The Help Center article, marked updated five days before this September 10 review, expressly permits selling through a third-party payment processor. The Sites developer guide still lists enabling financial transactions among unsupported uses.[^1][^3] The newer, specific payment guidance argues against declaring all commerce prohibited. The inconsistency still needs resolution against current applicable terms before relocating GALX's payment-enabled application. A successful Sites tool call does not settle that issue.

This finding is not a reason to block a read-only, synthetic client demonstration. Keep the first experiment independent of payments and sensitive data, and evaluate payment integration separately if the product requires it. The experiment should also verify the exact hosting/runtime requirements rather than assuming an existing Next.js deployment artifact is portable.

## Recommended experiment and decision gates

1. Select one repeated buyer job, such as a client project-status portal. Specify completion and ongoing support requirements before building.
2. Prepare it in an isolated project with synthetic data and an explicit file allowlist. Exclude this private strategy, internal diagnostics and the GALX operational source. Do not assume `.vercelignore` controls a different hosting system's source push or artifact packaging.
3. Measure local build, verification and maintenance effort against the current delivery path. A saved Sites version would be the next reviewable milestone if subsequently requested; creating/pushing/saving still requires the appropriate Sites workflow and access.
4. Demonstrate a local revision and rebuild, then verify a separate deployment candidate when publication is requested. Preserve source portability and record the cost of moving hosts.
5. Confirm account limits, client ownership/handover options, recurring costs and permitted use before selling a supported deployment. Terminal read execution and a live relay-only local draft have passed. Qualify the bounded workflow's publication, recovery and cost controls before promising delivery. Native Codex inference remains blocked by its separate transport contract.
6. Charge for the bounded customer job only if it earns payment and renewal. Reject the hypothesis if customers can satisfy the same job themselves with acceptable effort or if maintenance consumes the fee.

A promising demonstration does not warrant moving GALX's live inference, billing and operational systems. Treat Sites as one candidate delivery target and retain the separately funded compute and support constraints from the commercial reset.
