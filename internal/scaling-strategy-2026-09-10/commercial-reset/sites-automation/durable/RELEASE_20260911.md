## Deployment and compatibility changes

`RELAY_SITES_OUTPUT_LIMIT_FORWARDING` now propagates explicitly from the installed federation service to its worker containers. The default is false. The released service sets it to true for bounded durable-job qualification. This flag means the relay forwards a ceiling; it does not mean the supplier honors it.

Forwarding is restricted to jobs requesting durable receipts. Ordinary chat requests carrying `max_tokens` retain their existing supplier payload, avoiding a regression caused by a supplier that rejects `max_output_tokens`. The application test exercises both paths against an actual local worker.

The release image is `galxai-relay:sites-release-20260911`, with Docker image ID `sha256:cc5eec01f149b8102c3989124bac1348c1339946d7b30dcd664facf6fc57fb22`. Both original worker volumes remain mounted. The old image, supervisor configuration, source archive and stopped-volume backups are retained in the host's private release journal directory. A single retained volume is still not replicated disaster recovery.

Application deployment `dpl_AQXmeJrjWmFg3rcVW9iBRhyULXUW` was built with production configuration and promoted to the existing `galx.ai` domain after reaching `READY`. The prior deployment, `dpl_5wQ9QKj7HEqee7fMkbRNgmMshrqq`, remains the recorded application rollback target. The isolated verification build used synthetic configuration and was not deployed.

## Live qualification and its limits

Two explicit synthetic generation probes used the newly deployed production federation at its loopback origin, `http://localhost:3001`. One requested a detailed 1,000-entry list with a required 64-token ceiling and explicit no reasoning. It failed with the normalized `job_error` result, and its committed receipt remains `unknown` with null usage. This new result does not independently identify the supplier's precise rejection reason. The earlier diagnostic had identified HTTP 400 for unsupported `max_output_tokens`.

The second probe requested only `OK`, without an output ceiling, to isolate metering and retention. It succeeded with 16 total tokens. This deliberately tiny probe does not establish a cost bound. The worker was paused, checked idle, stopped, replaced and resumed using the same state volume. The recovered receipt matched the original exactly.

After replacement, independent authenticated GET requests through `https://relay.galx.ai` matched both original receipts, including the unknown result. A fresh administrator contract check also passed through that HTTPS origin. Generation through that exact public origin and a production rate card is still not qualified. These read-only checks started no model request. The two explicit qualification requests do not count unrelated background service activity.

The completed receipt records a 30-day retention deadline; unknown usage has no automatic receipt-storage expiry. The test proves immediate recovery across worker replacement, not the passage of 30 days. Operator evidence is retained as hashes and sanitized observations; no passing activation assertion was invented. The normal application rule continues to retain a reservation when usage is unknown. These operator probes did not create production wallet reservations.

OpenAI documents `max_output_tokens` as an output upper bound for its Responses contract. That documentation does not establish support in this supplier connection. A different field name, local timeout or smaller customer quote is not evidence of supplier enforcement. [Official Responses reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create).

No valid customer session was used to mutate production billing.

## Staging incident

An optional lean-source staging operation failed on a Python cache file. A dependent deployment was mistakenly started anyway and created an unintended Vercel project named `application-source` from partial source. No environment files or credentials were copied to it. The project was deleted, and its deployment URL returned HTTP 404 afterward. The existing GALX production domains were not switched to that project. This record does not assert what could have been read while it existed; access was not tested then. The correct original GALX build was the release ultimately promoted.

## Metered activation follow-up recorded at release time

The list below records the old metered release contract. For the subsequent fixed-price mode, use [Sites rollout](../../../../../docs/maintainers/SITES_OPERATIONS.md#rollout); supplier ceiling and exact usage proof are not its activation prerequisites. The original observations above remain unchanged.

1. Obtain a supported supplier ceiling and prove it with an intentionally long bounded output. Alternatively, review actual fixed prepaid supply terms with no automatic overage, capacity limits and pricing before designing a different commercial gate. No such contract is assumed and the current activation validator still requires an enforced output ceiling.
2. Establish the supplier economics and configure a versioned customer rate card. Run the qualification on the exact production HTTPS origin, selected model, rate version and output ceiling. Retain authoritative usage, exact receipts and recovery evidence; publish the customer-facing tariff before billing.
3. Add and test a server-enforced cohort allowlist before turning on paid generation. The present activation flag and qualification validator are global; they do not select accounts. Default-deny access to new quotes/generation for accounts outside the reviewed cohort while preserving authenticated recovery of existing operations.
4. Refresh the customer-owned native upload/receipt/private-update evidence, bind the evidence digest to the matching configuration and enable only the reviewed `native_host` cohort when every gate passes. Keep a tested pause and reconciliation procedure.
5. Qualify `cli` separately only after the supported upload mechanism changes and passes a fresh private save/update test. Do not convert the previous direct-call failures into a passing flag.

Keep operational journals, credentials, source diagnostics and these assessments private. Public material describes deliverables, prices, accepted limits and customer actions.
